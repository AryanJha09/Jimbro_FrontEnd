# JimBro

JimBro is a Flutter fitness-coaching client for onboarding, workout templates
and active sessions, nutrition logging, progress/history, profile management,
and Atlas coaching insights. It supports a credential-free mock mode for local
development and a FastAPI-backed mode for deployed environments.

## Repository boundary

This repository contains the Flutter frontend only. The companion FastAPI
source, Supabase schema, migrations, triggers, row-level-security policies, and
backend tests are owned and deployed from the separate backend repository.
They must not be recreated in this checkout. The backend is currently treated
as frozen; frontend changes must preserve its deployed contracts.

The authoritative API contract is the OpenAPI document generated by the
companion FastAPI repository/deployment. Obtain that deployment's
`openapi.json` from the backend owner and compare it with the client routes
before changing request or response models. `BACKEND DOCUMENTATION.docx` is a
legacy endpoint index, and
[`docs/BACKEND_ATLAS_ONBOARD_CONTRACT_REQUEST.md`](docs/BACKEND_ATLAS_ONBOARD_CONTRACT_REQUEST.md)
records required identity/onboarding invariants; neither replaces generated
OpenAPI, schema migrations, or backend tests.

## Supported platforms and auth

Flutter projects are checked in for Android, iOS, web, macOS, Windows, and
Linux. Web and iOS are the currently release-verified targets. Android requires
a configured Android SDK; desktop targets are scaffolded but require platform
QA before release.

Supported runtime modes:

| Backend mode | Auth mode | Purpose |
| --- | --- | --- |
| `mock` | unset or `fastApi` | Local fixture-backed development without live credentials |
| `fastapi` | `fastApi` | FastAPI email/password session and protected API calls |
| `fastapi` | `supabase` | Supabase direct auth supplies the bearer token used by FastAPI |

## Environment variables

Copy `.env.example` to `.env` and set only client-safe values. `.env` is bundled
as a Flutter asset, so it must never contain service-role keys, database URLs,
JWT secrets, passwords, or private API keys.

- `APP_BACKEND_MODE`
- `AUTH_MODE`
- `FASTAPI_BASE_URL`
- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`
- `SUPABASE_REDIRECT_SCHEME`
- `SUPABASE_REDIRECT_HOST`

`FASTAPI_BASE_URL` must contain `/api/v1` exactly once. Mock mode does not need
live backend values. Redundant and trailing path slashes are normalised before
Dio is created. Release builds reject loopback hosts.

Use an address reachable from the selected target:

| Target | Development API host |
| --- | --- |
| iOS Simulator | `127.0.0.1` may reach the development Mac |
| Physical iPhone | use the Mac's LAN address or a TLS development URL; `127.0.0.1` points to the phone |
| Android emulator | use the emulator's host alias when the backend runs on the development machine |
| Web | use a CORS-enabled URL reachable by the browser |
| Profile/release | use the deployed HTTPS API; never use a loopback address |

The iOS target has no broad App Transport Security cleartext exception. Prefer
HTTPS. If local HTTP is unavoidable, add only a development-scoped exception
for the exact development host and do not ship it in release configuration.

## Setup

```sh
flutter --version
cp .env.example .env
flutter pub get
flutter run
```

Select a target explicitly when needed, for example `flutter run -d chrome` or
`flutter run -d ios`. Never print `.env` contents in build logs or bug reports.

## Architecture

```text
lib/
├── app/                 MaterialApp, theme, and route registration
├── core/
│   ├── config/          environment parsing and validation
│   ├── errors/          stable client error mapping
│   ├── navigation/      bootstrap state and the application draft controller
│   ├── network/         Dio client configuration
│   ├── notifications/   workout reminder integration
│   ├── nutrition/       target calculations
│   └── repositories/    repository contracts, mock adapters, and FastAPI adapters
├── features/            auth, onboarding, home, workouts, nutrition, history,
│                        profile, and Atlas presentation/application code
└── shared/              reusable components and domain/view models
```

Riverpod is the state-management boundary. `AppDraftController` owns the
authenticated aggregate and coordinates repository calls;
`AppBootstrapState` is the navigation truth for authentication, provisioning,
onboarding, and readiness. Feature providers own async insights, workout
history, active-workout checkpoints, and onboarding. Repositories remain the
boundary between widgets/providers and mock or FastAPI data sources. The home
shell creates tabs lazily and retains each visited tab's state.

## Route map

| Route/state | Destination |
| --- | --- |
| bootstrap state | splash, auth, onboarding, or authenticated shell |
| authenticated shell tabs | Home, Workouts, Nutrition, History/Analytics, Profile |
| `/atlas` | Atlas chat |
| `/app/workouts` | authenticated shell with Workouts selected |
| `/app/workouts/templates/new` | new template builder |
| `/app/workouts/templates/:id/edit` | existing template builder |
| `/app/workouts/session/:id` | active workout |
| `/app/workouts/session/:id/end` | workout completion summary |
| `/app/workouts/history` | completed workout list |
| `/app/workouts/history/:id` | read-only workout detail |
| `/debug/onboarding-preview` | debug-build-only onboarding preview |

Workout route parsing lives in
`lib/features/workouts/presentation/workout_routes.dart`; global registration
lives in `lib/app/app.dart`.

## Local-only and fallback behavior

- Mock mode uses fixture repositories and requires no live credentials.
- Workout schedule data can fall back to per-account local persistence when the
  deployed schedule route is unavailable; the UI labels it as device-local.
- Hydration is currently screen-local and is not synced.
- Active-workout checkpoints and supported mutation outboxes use local storage
  for recovery; live backend responses remain authoritative after sync.
- No local fallback may replace an authoritative live empty, validation error,
  or backend-owned nutrition total.

## Tests and performance checks

```sh
flutter analyze
flutter test
flutter test test/responsive_regression_test.dart
flutter test test/performance_regression_test.dart --reporter expanded
```

The responsive suite uses fixture providers and covers supported authenticated
screens across compact widths, orientations, text scales, keyboard insets,
long strings, and empty/loading/error/large-data states. The performance suite
prints comparative fixture timings without using wall-clock thresholds as
pass/fail assertions.

## Migrations and deployment order

This frontend has no database migrations. For a coordinated release:

1. Author, review, back up, and apply schema migrations in the backend
   repository using its documented migration tool.
2. Deploy the compatible backend and verify its generated OpenAPI and backend
   test suite.
3. Run the non-sensitive live smoke checks against the deployed API.
4. Build and release this Flutter client only after the required contract is
   available.

Do not place SQL, service-role operations, or backend migration substitutes in
this repository.

## Release preflight

Follow [`RELEASE_CHECKLIST.md`](RELEASE_CHECKLIST.md). At minimum:

```sh
flutter analyze
flutter test
flutter build web --release
flutter build ios --debug --no-codesign
# On an Android-SDK-equipped machine:
flutter build apk --debug
```

Then run mock and live smoke paths, verify notification behavior on target
devices, check that no secret or bearer token appears in logs, and confirm the
deployed OpenAPI matches the client contract.

## Rollback

- Frontend: stop distribution, restore the previous signed build/hosting
  artifact, and re-run its smoke matrix against the still-compatible backend.
- Backend/database: use the companion repository's rollback/runbook and backup
  policy. Do not attempt database rollback from this frontend checkout.
- If a migration is not safely reversible, deploy a forward-compatible backend
  fix first, then roll back the client only after compatibility is verified.

Record the released frontend revision, backend revision/OpenAPI artifact,
migration version, environment, and smoke results together so rollback does not
guess at cross-repository compatibility.
